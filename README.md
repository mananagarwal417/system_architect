# System Architect — Visualize & Explain System Architecture

A small web app for creating, visualizing and describing system architecture diagrams and design artifacts, with optional AI-powered explanations. It’s intended for engineers who want to capture architecture sketches, store designs, and ask the system to produce human-readable explanations.

## Quick summary
- Users can sign up / sign in, create architecture and design records, and request natural-language explanations generated by an AI service.
- The repository contains a JavaScript backend (REST API) and a JavaScript frontend (single-page app).

---

## Stack
- **Language(s):** JavaScript (primary)
- **Framework / runtime:** Node.js + Express-style REST API for the backend; frontend is a JavaScript SPA (framework not explicitly listed but implemented under `frontend/`)
- **Notable pieces:**
  - Backend entry: `backend/index.js`
  - REST route groups: `backend/routes/*`
  - Controllers: `backend/controllers/*`
  - Business logic / AI integration: `backend/services/*` (notably `aiService.js` and `explainService.js`)
  - Models (persistence): `backend/models/*` (`Architecture.js`, `Design.js`, `User.js`)
  - DB and OpenAI configuration: `backend/config/db.js`, `backend/config/openai.js`
  - Middleware: `backend/middleware/authMiddleware.js`

## How it’s organized

Top-level (relevant) tree:
```
backend/                Express REST API, models, controllers, services
  index.js              App entry point (starts server & registers middleware/routes)
  package.json
  package-lock.json
  config/
    db.js                Database connection/config
    openai.js            OpenAI / AI configuration helper
  controllers/
    authController.js    Login / signup endpoints
    architectureController.js  CRUD and serve architecture data
    designController.js  CRUD for design artifacts
    explainController.js Endpoint that generates/exposes AI explanations
  middleware/
    authMiddleware.js    Auth guard (protects routes)
  models/
    User.js              User model
    Architecture.js      Architecture model (diagram/data)
    Design.js            Design model (detailed design artifacts)
  routes/
    authRoutes.js
    architectureRoutes.js
    designRoutes.js
    explainRoutes.js
  services/
    aiService.js         OpenAI client code / prompt construction
    explainService.js    High-level logic to call aiService and format responses

frontend/               Single-page app UI (connects to backend API)
  (frontend application files — builds UI, visualizes diagrams, calls API)
```

How it fits together (runtime shape):
- The backend is an HTTP server (Node.js) that exposes REST endpoints grouped in `routes/*`. Each route maps to controller functions in `controllers/*` which validate/parse requests, call business logic in `services/*`, and persist/read domain objects in `models/*`.
- `aiService.js` and `explainService.js` encapsulate the AI integration (OpenAI) and are used by `explainController.js` to return natural-language explanations for saved architecture/design items.
- Frontend (SPA) calls the backend API to authenticate users and to create/read/update architecture and design records and to request AI explanations.

## Data flow and architecture (detailed)

1) High-level components
- Client (browser SPA) — renders UI, creates diagrams, sends requests.
- Backend API — routes -> controllers -> services -> models -> DB.
- Database — stores Users, Architectures, Designs.
- AI provider (OpenAI) — called by `aiService.js` for explanations.

2) Typical request flows

a) User authentication
- Client -> POST /auth/register or POST /auth/login (authRoutes -> authController)
- authController validates payload, interacts with User model to create/verify user, issues auth token (middleware/authMiddleware enforces protected endpoints).
- Response includes auth token used by client for future requests.

b) Create / fetch architecture
- Client -> POST /architectures (architectureRoutes -> architectureController)
- Controller validates payload (diagram JSON / metadata), saves to Architecture model, returns created resource with ID.
- Client GET /architectures/:id to retrieve details (controller reads from DB).

c) Request explanation (AI)
- Client -> POST /explain (explainRoutes -> explainController) with target resource id and optional prompt/context.
- explainController calls explainService, which:
  - loads the Architecture/Design from models,
  - builds a prompt/context,
  - calls aiService (which calls the configured OpenAI endpoint via `backend/config/openai.js`),
  - receives response, post-processes it,
  - returns a structured explanation to the controller which returns it to the client.
- Explanation may be stored as part of the Design/Architecture record or returned transiently.

3) Data/Control diagram (ASCII)

Client (SPA)
   |
   |--[HTTP JSON requests: auth, architectures, designs, explain]-->
   v
Backend API (Express)
   routes/ -> controllers/
     controllers validate -> call services/
        services (explainService, aiService, others)
           |
           |---> aiService -> OpenAI API (external)
           |
        services -> models (CRUD)
           |
        models -> Database (Mongo/Postgres/other)
   |
   v
Responses (JSON) -> Client

4) Security & middleware
- `authMiddleware.js` protects create/update/delete endpoints and ensures token/credentials are valid.
- Sensitive configuration (DB URI, OpenAI API key, JWT secret) should be provided through environment variables (see *Required env vars* below).

## How to run (shortest path)
1. Backend
- From repo root:
  ```bash
  cd backend
  npm install
  # start with
  npm start
  # or
  node index.js
  ```
- Required (example) environment variables:
  - PORT (e.g. 3000)
  - DATABASE_URL or MONGODB_URI (value consumed by `config/db.js`)
  - OPENAI_API_KEY (used by `config/openai.js` and `services/aiService.js`)
  - JWT_SECRET (used by auth middleware and controllers)

2. Frontend
- From repo root:
  ```bash
  cd frontend
  # install and start (framework-specific commands)
  npm install
  npm start
  ```
- The frontend should be configured to call the backend API host/port (CORS may be required).

If you prefer Docker or a one-command setup, add a docker-compose file that brings up DB + backend + frontend and wires env vars.
